# 为什么不做 GraphRAG

> 结论：**买得起，但不划算。** 这是 ROI / 排期决策，不是预算决策。

## 成本

以本项目 1,000 篇 / 约 4,800 chunks 为口径：

| 项 | 估算 |
|---|---:|
| 实体/关系抽取（每 chunk 一次） | 约 $0.25–0.30 |
| 实体摘要 + Leiden 社区报告 + JSON 解析重试（按 2×） | 约 $0.55–1.00 |
| 150 题 global search | 约 $0.50–1.50 |
| **合计** | **约 $1.11** |

$1.11 只占 $10 预算的 11%，所以「太贵」不是理由。

## 真正的理由

1. **收益无法兑现**：GraphRAG 的强项是「跨大量文档的全局主题总结」。本项目每篇文档只有 2–12 个 chunk（中位 4），
   1,000 篇的实体图社区会很薄，社区报告容易变成空话。
2. **替代品足够好**：r6 RAPTOR 的索引成本约 $0.08–0.15（1/10–1/14），同样提供摘要层，直接覆盖全局综述题。
3. **工程风险高**：抽取格式解析失败会产出空图；实体归一化、Leiden 依赖、社区报告长度都要调。
   在 30 题评测集上，这些调试成本换不来可测的提升。
4. **排期**：把时间花在 9 个可比较的 rung 上，比花在 1 个高成本 rung 上信息量更大。

## 报告里怎么写

> 「GraphRAG 未实现：不是预算不足，而是在 1,000 篇 / 4,800 chunk 的语料上，实体图的社区结构过薄，
> 其全局总结收益无法超过 r6 RAPTOR，且工程风险显著更高。若语料扩到 10,000 篇以上，应重新评估。」

这样写，读者不会误以为「RAG 发展史到 GraphRAG 就买不起了」。
