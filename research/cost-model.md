## 2. 计价公式

### 2.1 单次调用成本

```
cost(in, out, cached) = (in − cached) × 1.5e-7
                      + cached        × 3.0e-9
                      + out           × 6.0e-7
```

其中 `1.5e-7 = 0.15/1e6`，`6.0e-7 = 0.60/1e6`，`3.0e-9 = 0.003/1e6`。

### 2.2 基线生成输入

```
I_base = 66（system）
       + 5（“问题：/资料：”固定文案）
       + 31.7（加权问题）
       + 2,222.0（top-5 上下文）
       + 8（chat 角色格式开销）
       = 2,332.7 token
O_base = 134.2（按题型加权的回答长度）
```

回答长度假设（按题型，单位 token）：single 120、entity 45、multi 170、global 420、none 12。
加权：`(60×120 + 30×45 + 30×170 + 15×420 + 15×12) ÷ 150 = 134.2`。

### 2.3 各阶段输入/输出公式

| 阶段 | 查询侧公式 | 索引侧公式 |
|---|---|---|
| S1 | `1 × (I_base, O_base)` | 无 |
| S2 | `1 × (I_base, O_base)` | 无（BM25/rerank 免费） |
| S3 | `HyDE: (70+31.7, 300)` + 生成 `(I_base, O_base)` | 无 |
| S4 | `改写: (74+31.7, 80)` + 生成 `(I_base, O_base)` | 无 |
| S5 | `1 × (I_base + 5×75, O_base)` | `869 × (91+8+1,723.6+432.1, 75)` |
| S6 | `1 × (I_base + 250, O_base)` | `97 × (64+9×432.1, 250)` + `11 × (64+9×220, 250)` |
| S7 | `评分 (52+31.7+2,222, 15)` + 生成 `(I_base, O_base)` + 30%×(改写 `(70+63.4, 30)` + 重生成 + 重评分) | 无 |
| S8 | `3.2 × (3.0 × I_base, ~60/步)` + 最终回答 | 无 |
| S9 | `路由 (60+31.7, 8)` + 按 40/30/20/10 路由到 S1/S2/S7/S8 | 无 |

S5 的 75 token 是 contextual 前缀的目标长度（规格 50–100 token，取中值）；它同时让查询侧上下文增加 `5×75=375` token。

### 2.4 S5 缓存假设

索引 prompt 的结构是“固定 system → 文档 → 片段”。同一文档的 4–10 个 chunk 共享文档前缀，因此同一文档的第 1 次调用写入缓存，后续调用按 `$0.003/M` 读：

- 200 个文档各 1 次全价：`200 × 2,254.7`
- 其余 `869 − 200 = 669` 次，文档部分 1,723.6 token 命中缓存
- 缓存读 token：`669 × 1,723.6 = 1,153,105`
- 未命中输入：`1,959,356 − 1,153,105 = 806,251`

成本：

```
806,251 × 1.5e-7 = 0.120938
1,153,105 × 3.0e-9 = 0.003459
65,175  × 6.0e-7 = 0.039105
合计 = 0.163502
```

不缓存则为 `0.293903 + 0.039105 = 0.333008`，即缓存省 **$0.1695**。前提是同一文档的 chunk 连续处理，且缓存 TTL（5–10 分钟）未过期；按 8 并发估算单文档秒级完成，成立。

### 2.5 S6 调用数推导

```
L1 = ceil(869 / 9) = ceil(96.56) = 97
L2 = ceil(97 / 9)  = ceil(10.78) = 11
合计 = 108 次
```

L1 单次输入 `64 + 9×432.1 = 3,952.9`；L2 单次输入 `64 + 9×220 = 2,044`（假设 L1 摘要 220 token）。
总输入 `97×3,952.9 + 11×2,044 = 383,431 + 22,484 = 405,915`；总输出 `108×250 = 27,000`。

### 3.1 各阶段说明与假设

**S1 / S2（$0.0646 / 150 题）**
- 只有 1 次生成调用；BM25、RRF、bge-reranker-v2-m3 均不产生 LLM 费用。
- S2 与 S1 的 token 完全相同（top-5 数量不变），成本差为 **$0**；差别只在延迟（+0.35s rerank）和检索质量。
- 索引成本为 0，因为 embedding 免费。

**S3 HyDE（$0.000626/题，1.46× S1）**
- 1 次生成假设文档调用（300 token 输出）+ 1 次回答生成。
- HyDE 生成的内容不进入最终上下文，只用于检索；因此只增加一次调用，不增加生成侧上下文。
- 成本增量主要来自 300 token 输出（`300×6e-7 = $0.00018`）。

**S4 Multi-query / RAG-Fusion（$0.000494/题，1.15× S1）**
- 假设 1 次调用批量产出 3 条改写（不是 3 次独立调用），输出 80 token。
- 若改成 3 次独立调用（每次输入 105.7），每题增加 `2×105.7×1.5e-7 = $0.000032`，可忽略；**批处理的价值在延迟与限流，不在钱**。
- 融合后仍只生成 1 次。

**S5 Contextual Retrieval（索引 $0.1635，查询 $0.000487/题）**
- 869 次索引调用，每次输入 = 整篇文档 1,723.6 + chunk 432.1 + prompt 99 + chat 8 = 2,254.7。
- 输出 75 token/次（50–100 token 前缀）。
- 查询时前缀随 chunk 一起进入上下文，+375 token/题，使输入从 2,332.7 升到 2,707.7（+16%）。
- **这是全项目唯一“按 chunk 数线性增长”的索引成本**。在 869 chunk 规模下只有 $0.16；若语料扩到 2,000 篇（约 5,000 chunk），按同口径约 $0.94。

**S6 RAPTOR（索引 $0.0771，查询 $0.000468/题）**
- 97 个 L1 摘要 + 11 个 L2 摘要 = 108 次调用。
- 输入按 9 chunk/簇计算；输出 250 token/摘要（150–250 字）。
- 查询时假设 top-5 中 1 个是摘要节点，上下文 +250 token。
- 若改用 8 chunk/簇：L1=109，L2=14，总 123 次，索引约 $0.0874；若 10 chunk/簇：L1=87，L2=9，共 96 次，约 $0.0747。**簇大小对成本不敏感**。

**S7 Self-RAG / CRAG（$0.001031/题，2.4× S1）**
- 每题固定：1 次评分（输入 2,305.7，输出 15）+ 1 次生成。
- 假设 30% 的题评分失败，触发 1 次改写（133.4 in / 30 out）+ 1 次重生成 + 1 次重评分。
- 平均调用数 `2 + 0.3×3 = 2.9`。
- 成本对失败率敏感：失败率 15% → $0.00091/题；50% → $0.00120/题（见 §8）。
- 弃答题（none，15 题）只输出 12 token，已计入加权输出。

**S8 Agentic ReAct（$0.001238/题，2.9× S1）**
- 按“平均 3.2 步、总输入 3.0×I_base”建模：多步轨迹会反复携带历史，输入增长快于步数。
- 输出 = 3 步思考/动作 × 60 + 最终回答 134.2 = 314.2。
- 上限 5 步时（最坏情景）成本约 $0.0019/题，150 题 $0.29。
- 这是**单题方差最大的阶段**：简单题 1 步即答，复杂题 5 步。

**S9 Adaptive router（在线 $0.000649/题；离线仅 $0.0000181/题）**
- 在线模型：1 次路由（91.7 in / 8 out）+ 按 40% S1、30% S2、20% S7、10% S8 路由后的加权成本，平均 2.6 次调用。
- **推荐离线评估**：8 个阶段的答案已缓存，路由只需对 150 题各做 1 次分类（$0.002716），答案直接复用对应阶段输出，不需要重新生成。这样 S9 的边际成本从 $0.0974 降到 $0.0027。

## 4. GraphRAG：估算与排除理由

按 869 chunk、`max_gleanings=0` 估算：

| 环节 | 调用数 | 输入/次 | 输出/次 | 输入合计 | 输出合计 |
|---|---:|---:|---:|---:|---:|
| 实体/关系抽取 | 869 | 700 | 400 | 608,300 | 347,600 |
| 实体描述摘要 | 2,500 | 280 | 100 | 700,000 | 250,000 |
| 社区报告 | 200 | 2,000 | 600 | 400,000 | 120,000 |
| **合计** | **3,569** | | | **1,708,300** | **717,600** |

```
索引成本 = 1,708,300×1.5e-7 + 717,600×6e-7
         = 0.256245 + 0.430560
         = 0.686805
```

查询侧：85% local（4,000 in / 119 out），15% global（50 篇社区报告 map-reduce，100,000 in / 300 out）：

```
in  = 0.85×4,000 + 0.15×100,000 = 18,400
out = 0.85×119   + 0.15×300     = 146.15
$/题 = 18,400×1.5e-7 + 146.15×6e-7 = 0.002760 + 0.0000877 = 0.002848
150 题 = 0.427153
```

**GraphRAG 总计 ≈ $1.114**（索引 $0.687 + 查询 $0.427），相当于期望总预算的 43%。

排除理由（按重要性）：

1. **ROI 低**：$1.11 的增量只对 15/150 道全局题有理论增益；按题型摊薄，每题全局题成本 $0.074，而 S6 RAPTOR 的全局增益成本是 $0.077 一次性（摊到 150 题几乎为 0）。
2. **工程复杂度**：实体归一化、Leiden 社区检测、社区报告层级、local/global 两套查询路径，至少 2–3 天，且失败模式（空图、解析失败、社区过少）会污染主榜。
3. **不是“买不起”**：$1.11 完全在 $10 内。如果全局题是核心卖点且时间充裕，可以加；否则优先 RAPTOR。

> 结论：**排除 GraphRAG 是排期决策，不是预算决策。** 报告里应这样写，避免“因为太贵所以不做”的错误归因。

## 6. Token 口径、公式与假设清单

### 6.1 口径

1. **编码器**：`cl100k_base`（与切分、`build_context` 一致）。DeepSeek 实际 tokenizer 可能不同，全文统一按 ±10% 不确定度处理。
2. **固定文案**：逐条用 tiktoken 实测（§1.5），不用字符数估算。
3. **上下文**：300 次随机 top-5 抽样的均值 2,222.0；这是“检索结果长度分布”的无偏代理，但不是真实检索结果。真实 top-5 若更长，最大 2,611（+17.5%）。
4. **输出长度**：按题型假设，不是实测；这是本模型最大的单一不确定源。
5. **chat 格式开销**：每次调用 +8 token（role/分隔符）。对总成本影响 < 0.4%。
6. **缓存**：仅 S5 文档前缀使用缓存；查询侧上下文每题不同，缓存命中率按 0 计（固定前缀仅 71 token，收益 < $0.01，不值得优化）。

### 6.2 核心公式汇总

```
① 单题查询成本
   C_q(stage) = Σ_calls [ (in_i − cached_i)×1.5e-7 + cached_i×3e-9 + out_i×6e-7 ]

② 一次性索引成本
   C_idx(stage) = calls × [ (in − cached)×1.5e-7 + cached×3e-9 + out×6e-7 ]

③ N 题单轮成本
   C_run(stage, N) = N × C_q(stage)

④ 阶梯累计（按构建顺序）
   Cum(k) = Σ_{s≤k} C_idx(s) + 150 × Σ_{s≤k} C_q(s)

⑤ 总预算
   Total = (eval_gen + corpus_prep + C_idx(S5) + C_idx(S6)
            + dev + final + judge + s9_offline) × 1.20
```

### 7.1 精确缓存键（可直接实现）

**查询答案缓存**

```python
key = sha256(canonical_json({
    "v": 1,
    "kind": "query_answer",
    "model": "deepseek-v4.1-flash",
    "prompt_id": prompt_id,            # sha256(规范化模板)[:16]
    "temperature": 0,
    "max_tokens": 512,
    "stage": "S7",
    "index_version": index_version,    # 见下
    "qid": "q-0042",
    "question_sha256": sha256(question),
    "retrieved_chunk_ids": sorted(chunk_ids),
    "top_k": 5,
}, sort_keys=True))
```

**索引缓存（S5 / S6）**

```python
key = sha256(canonical_json({
    "v": 1,
    "kind": "context_prefix",          # 或 "raptor_summary"
    "model": "deepseek-v4.1-flash",
    "prompt_id": prompt_id,
    "temperature": 0,
    "corpus_sha256": corpus_sha256,    # manifest 已有
    "chunk_id": "person-xxxx:003",
    "doc_sha256": sha256(full_doc_text),
    "chunk_sha256": sha256(chunk_text),
    "context_version": 1,
}, sort_keys=True))
```

**Judge 缓存**

```python
key = sha256(canonical_json({
    "v": 1, "kind": "judge",
    "judge_model": "deepseek-v4.1-flash",
    "prompt_id": judge_prompt_id,
    "qid": qid, "stage_a": "S1", "stage_b": "S2",
    "answer_sha256_a": ..., "answer_sha256_b": ...,
    "order": "AB",                     # 或 "BA"
    "temperature": 0,
}, sort_keys=True))
```

规则：

- **不要用原始 prompt 全文做 key**：空白/换行变化会造成假 miss。用 `prompt_id + 结构化输入`。
- `index_version = sha256(corpus_sha256 + chunk_size + overlap + embedding_model + bm25_params)[:16]`；任何一项变化都必须换版本。
- 缓存条目存 `response / usage / prompt_id / created_at / cost`，便于与账单对账。
- 索引缓存**不设 TTL**；查询缓存按 `index_version` 失效。
- Judge 缓存必须含 `order`，否则 AB/BA 会互相覆盖。

### 7.2 Prompt 版本化

- 模板存文件（`prompts/*.md`），`prompt_id = sha256(规范化文本)[:16]`；规范化 = 去行尾空白 + 统一 `\n`。
- 任何语义修改（哪怕一个词）都换新 ID，**禁止原地复用**。
- 每条结果行记录 `prompt_id`，报告里按 `prompt_id` 聚合；否则无法解释“同一阶段两轮分数不同”。
- 建议在 CI 里跑一个快照测试：模板 hash 变化时打印 diff 并阻断自动重跑，防止误烧索引钱。

### 7.3 50 题分层子集

按当前分布抽取：

| 题型 | 50 题子集 | 150 题全集 |
|---|---:|---:|
| single | 20 | 60 |
| entity | 10 | 30 |
| multi | 10 | 30 |
| global | 5 | 15 |
| none | 5 | 15 |

用法：

- **全量跑**：S1、S2、S5、S6（便宜、方差小、作为分母）。
- **子集先跑**：S3、S4、S7、S8、S9（贵或方差大）。只有子集上相对基线提升超过 bootstrap 95% CI 下界，才晋级到 150 题。

### 7.4 免费层

- bge-m3 与 bge-reranker-v2-m3 在 SiliconFlow 上按 **$0** 计；¥10（约 $1.4）钱包视为独立预算，不计入 $10 LLM 上限。

- 若免费层未来收费，最坏情况也只是从 ¥10 钱包扣，不影响 LLM 预算结论。

| 任务 | 串行 | 8 路并发 | 备注 |

## 附录 B：为什么不是“每个阶段 ×1.4”这种拍脑袋倍数

本模型对每个阶段都从“调用次数 × 每次输入/输出 token × 单价”重算，而不是给 S1 乘系数。差异示例：

- S2 相对 S1 的真实倍数是 **1.00×**（rerank 免费、无额外 LLM 调用），不是文档里写的 1.2×；
- S5 的查询倍数是 **1.16×**（仅上下文 +375 token），索引是一次性 $0.16；
- S7 的倍数是 **2.40×**（2.9 次调用、6,060 输入），不是 1.4×；
- S8 的倍数是 **2.88×**（3.2 次调用、3× 输入），与“3–5×”区间一致但更精确。

这类差异会直接改变“哪个阶段值得做”的排序，因此必须逐项算，不能乘系数。
