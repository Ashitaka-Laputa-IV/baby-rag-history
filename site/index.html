WHY A LADDER

不是九套代码，
是九张工序单。

每个里程碑只回答一个问题：在同一个检索循环里，再加一个动作，究竟值不值？

01

一张图

plan 产出有序阶段表，dispatch 读 plan[cursor] 决定下一步。新增 rung，通常只是在表里加一行。

02

一个变量

从 dense 到 hybrid，从 rerank 到 contextual，每个台阶只增加或替换一个检索动作，方便看差值的来源。

03

同一把尺子

所有 rung 共用 30 道题、top-5 / 4,000-token 上下文、同一个 judge 和同一套 cold cost 计算。

04

不吹 SOTA

这是可读的实验装置，不是排行榜。样本小、语料单一，结论只对这套设置负责；报告里会明确写边界。

ONE GRAPH

九个计划，
共用一条流水线。

plan → dispatch 是唯一骨架；每个阶段做完 cursor + 1，回到工头。越界就进 finalize。

19 nodes 32 edges 4,000 tokens

rung 是一行计划，
不是一张图。

新增一个检索里程碑，通常只要在 RUNGS 里加一行；只有新增节点，才需要改图。

  • plan 只产出 plan 和 cursor。
  • dispatch 是唯一路由点，读 plan[cursor]。
  • agentic 是带 4 步循环的普通节点，不是子图。
  • 所有 rung 最终固定 top-5 / 4,000 token。

COMPOSITE SCORE

原题 30 · 原索引

r5 Contextual Retrieval 最高：100% 可答 acc、85.2% evidence R@1。 完整表 ↗
r5 为什么强给 chunk 补语境，检索时不必只靠标题和局部词面。
r2 的性价比同样的 cold cost 量级，换来 96.3% 可答 acc；适合作为默认起点。
masked 的提醒去掉标题线索后，综合分整体掉约 20–24 分；标题泄漏很真实。

RUN IT

先跑一题，
再决定要不要相信它。

数据默认不入库；按 README 从 rag-ladder 复制，或用脚本重建。没有 key 也可以先跑 babyrag info。

01 · install
git clone https://github.com/Ashitaka-Laputa-IV/baby-rag-history.git
cd baby-rag-history
uv sync
cp .env.example .env      # OpenCode Go + SiliconFlow keys
uv run babyrag info
02 · ask
uv run babyrag ask "增禄的父亲咸成曾任什么官职？" \
  --rung r5_contextual

# 或从 r0 开始，沿台阶比较
uv run python -m scripts.run_eval \
  --rungs r0_dense,r2_rerank,r5_contextual \
  --workers 2

需要 OPENCODE_GO_API_KEY 和 SILICONFLOW_API_KEY；judge 与生成模型、embedding/reranker 是分开的。
